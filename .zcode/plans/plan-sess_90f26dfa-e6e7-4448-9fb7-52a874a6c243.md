# 多 Provider 连接共存与会话级热切换

## 目标（你的两点诉求）

1. **配置记忆完整呈现**：已配置的 provider/模型集合在每次打开时全部就位。只有从未配置过（零连接）才出现引导横幅，之后永不强制进入配置。
2. **多连接共存**：一次配置多个 provider（内置 openai/deepseek/glm + 多个自定义 endpoint），各自带凭证与模型清单，全部持久化。
3. **会话级热切换**：在 Composer/设置中按 (provider, model) 切换当前会话的路由——**零 Runtime 重建、不要求结束活跃回合**（回合间生效，沿用引擎既有的回合路由冻结语义）。
4. 添加/移除连接是罕见操作：保留"工作区空闲才可执行"约束和 Runtime 重建，但**不再强制重绑所有会话的模型选择**（现有 `RebindWorkspaceProfiles` 删除）。

## 架构事实（探索结论，改动面比预想小）

引擎层**已经支持**多路由：`RouteSet` 按回合冻结、`SelectableRoutes[RouteKey(provider,model)]` + `WithAct()` 热重解析、`SessionProfile` 本就携带 provider+model 字段、provider router 按请求分发、egress gate 可授权 N 个主机、凭证按 provider 分 keyring 命名空间（多 provider 的 key 天然共存）。

真正的钳制点只有五处：
- `wire/model_catalog.go` `runtimeSelectableRoutes`——可选项只注册单一 provider；
- `wire/route.go` `resolveExecRoute`——自定义 endpoint 只建单 provider 目录；
- `host/web/setup.go`——单个 `selection.json`（标量 provider）；
- `workspace_manager.go` `replaceSelection`——全量重建 + 强制重绑会话；
- `provider_deadline.go`——单凭证 live resolver。

## 实施阶段

### Phase 0：收尾启动竞态修复（上一问题）
客户端 `awaitWorkspaceReady` 轮询已写，补测试；桌面壳 spawn 模式下等 stdout 的 "Runtime Ready / Setup Ready" 行（而非 healthz）再开窗。

### Phase 1：持久化 v2→v3（`web-setup/selection.json`）
```json
{"version":3,
 "connections":[{"id","provider","base_url?","protocol?","model","models[]","model_metadata?","metadata_provenance","credential?"}],
 "default_connection":"id"}
```
v2 读取时无损升级为单条目 v3（沿用仓库 v1→v2 的显式升级先例与严格解码/规范化校验模式）。

### Phase 2：Runtime 多连接构建（wire）
- `resolveExecRoute` 构建多 provider catalog：内置目录 + 每个自定义连接 `AddProvider`（自定义连接 provider id = `openai-compatible:<端点标识>` 保证唯一）。
- `runtimeSelectableRoutes` 跨全部已配置连接注册路由，凭证按连接（`route.WithCredential(conn.credential)`），全部标记 hot；未配置的内置 provider 显示"需要添加连接"而非"需要重启"。
- `liveCredentialResolver` 扩展为多 controlled 引用（`map[ref]*credential.Control`，按请求携带的 ref 匹配，未匹配走 fallback）；`prepareWebCredentials` 每连接一个 Control（`OpenControl` 已按 provider 命名空间，rotation/commit/rollback per-connection 化）。

### Phase 3：连接管理与热切换（workspace_manager + API）
- 新 setupRPC：`connection/add|update|remove`（supervisor 级、无需 Runtime 就绪）；add/update/remove 触发 Runtime 重建（保留空闲约束）；**移除 `RebindWorkspaceProfiles`**——会话保留各自 (provider, model)；remove 时若仍有会话钉在被移除连接的模型上则拒绝（与现有 `model/remove` 保护语义一致）。
- `connection/status` → `connection/list`（旧路由兼容期内返回默认连接）；`setup/apply` 语义不变（首次配置 = 第一条连接 + 默认）；`model/add|remove` 限定所属连接。contract + `make web-protocol` 生成物同步再生成。
- 放开 `validateMutableProfilePatch` / `runtimeProfileModels` 到全部已配置 provider 的 hot 模型——引擎校验路径（`session_profile_validation.go`）无需改动。

### Phase 4：前端
- bootstrap 的 setupCatalog 增加每 provider 的已配置/凭证状态。
- Settings → Connection 改为**连接列表**（每条：provider、endpoint、默认标记、凭证状态、测试、删除）+ 添加连接（复用现有表单）+ 设为默认；"Apply and restart" 心智退场。
- Composer 模型选择升级为按 provider 分组的 (provider, model) 组合选择，切换走 `profile/update`（provider+model 一起 patch）。
- Models 设置页跨 provider 展示、按连接分组管理；引导横幅仅在零连接时出现。

### Phase 5：测试与验证
- Go：多连接 catalog/SelectableRoutes/多凭证 resolver 单测；连接增删、不重绑、移除保护测试；v2→v3 升级测试；contract 生成物与既有测试适配。
- Web：client/Settings/Composer 测试更新；e2e 增加双连接 fixture（内置 + 自定义 endpoint 各一）验证热切换。
- 全部门禁（unit/e2e/docs/experience/可复现构建）。

## 明确不做（边界）
- 回合**中途**切换路由（维持回合间生效的既有语义）。
- purpose 槽位（summary/vision/judge）跨连接路由——保持回退 act 路由的现状。
- 同一 provider 配多份凭证。

## 工作量估计
约 1.5–2.5 周；风险最高的一块是 Phase 2 的凭证多 Control 联动（rotation 状态机 per-connection 化），单独先行验证。
