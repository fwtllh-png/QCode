# 仓库理解专项评测

本评测验证作用域感知的跨文件引用候选能否减少同名误连，同时保留应有关系。
它是确定性的索引回归语料，不调用模型、语言服务器或网络，不代表端到端
代码理解水平、真实仓库准确率或完整调用图质量。

## 运行

```bash
make repository-understanding-eval
# 可选：指定报告位置
make repository-understanding-eval REPO_EVAL_REPORT=/tmp/qcode-repo-eval.json
```

默认生成 `.tmp/repository-understanding-report.json`。常规
`go test ./internal/persist/repoindex` 也会执行评测，只是不输出报告文件。

语料在 `testdata/repository-understanding/cases.json`。每个场景构造独立
临时仓库，通过生产索引入口完成提取、SQLite 持久化与关系解析，然后对比
人工标注的 `(source, destination, target)` 去重集合。测试要求每个文件
实际启用了作用域分析且未截断，并核对出现位置与源文件 digest。

同一次运行使用相同持久化符号和标识符计数，重放旧规则的全仓库同名关联，
作为基线。两组结果都记录 TP（正确关系）、FP（误连）、FN（漏连）、
precision 和 recall；分母为零时指标为 null。新增任何误连或漏连均导致
测试失败，不设置任意百分比门槛。报告含索引版本、语料 SHA-256、逐场景
缺失/多余关系和索引耗时。耗时仅作诊断，不作为性能门禁。

## 当前覆盖与结果

16 个场景覆盖 Go 包边界、显式导入别名、参数/块遮蔽、未知接收者、外部
测试包，以及 JS/TS 导入别名、命名空间导入、闭包、参数/解构遮蔽、块作用域、
var 提升、未绑定名称和 TSX 字符串干扰。

| 规则 | TP | FP | FN | precision | recall |
| --- | ---: | ---: | ---: | ---: | ---: |
| 原同名关联 | 7 | 20 | 0 | 25.9% | 100% |
| 作用域候选 | 7 | 0 | 0 | 100% | 100% |

这是受控语料结果，不能外推至真实仓库。评测只比较引用候选，不将独立存在的
import 依赖边计作符号使用，也不评估 Repo Map 排名或模型回答质量。

附加单元测试覆盖出现记录上限、泛型参数作用域、catch/循环绑定、方法声明
排除，以及修改文件后关系失效、删除清理、存储读取与旧派生 schema 重建。

## 后续扩展方式

先增加带明确人工证据的真实仓库片段，保持正例和负例配对，再扩大语言范围。
类型推断、重导出、构建别名等尚不支持的场景应作为明确的新能力加入，不能
通过删除正例来提高 precision。完整边界见[代码结构提取](./code-structure.md)。

模型层面的仓库问答、影响分析任务命中率和上下文成本，需要独立的任务标注
与端到端评测；当前这项测试不能替代它们。

## 真实源码任务评测

```bash
make repository-task-eval
# 可选：指定 JSON 输出路径
make repository-task-eval REPO_TASK_REPORT=/tmp/qcode-task-report.json
```

默认生成 `.tmp/repository-task-report.json` 和
`.tmp/repository-task-report.json.summary.md`。JSON 包含任务描述、标注、源码
摘要和每次工具调用的完整输入输出；Markdown 汇总对比结果及缺失/多余项。
报告可能含所选公开源码片段，本命令不读取工作区其他文件。

任务语料为 `testdata/repository-understanding/tasks.json`，目前从 QCode 的
repowalk、symbols 包选取 9 个完整源码文件，覆盖 6 个任务：二进制策略定位、
语言识别入口定位、Go 引用规则修改准备、读取上限修改准备，以及两个模块的
测试选择。每个任务都有预期文件、必要测试、源码证据锚点和标注理由。
标注由代理检查源码后编写，尚未经过独立人工复核。任务不植入虚构缺陷，
修改类任务评估的是准备修改所需的证据，不真正打补丁。

文本路线调用现有 `search_text`；结构化路线调用 `search_definition`、
`search_references` 和 `search_related_tests`。两条路线使用相同的源码子集、
结果预算与查询结果上限，各自使用独立临时目录和工具注册表。命令经过仓库
已有工具测试执行入口调用生产工具，不实现另一套搜索或引用分析算法。

这是**固定工具流程的任务证据评测**：关键词和调用顺序是预先编写的，任务
描述不经模型解释。报告 `model_executed=false`、`autonomous_task_success=null`，
不能据此声称 Agent 修复成功率提升。没有调用模型，也没有执行推荐测试。
真正的自主任务评测还需要冻结模型、提示、运行环境以及补丁验收条件。

评分分别记录：

- 文件 TP/FP/FN、precision、recall，以及缺失/多余路径；测试选择任务仅评测试文件。
- 必要测试文件命中、漏项与额外候选。按任务计数，不把“找到了测试”当作通过测试。
- 证据锚点命中：工具必须返回对应文件的相关行号，不能仅返回文件名就算找到证据。
- 每条固定路线的工具调用次数、参数与结果 UTF-8 字节数、逐调用耗时。
  字节不是 token，`model_tokens=null`；这些调用次数也不是 Agent 自主决策次数。

预算是语料公开配置：10000 的结果 token 预算沿用工具测试夹具，200 的
`max_results` 沿用索引默认查询上限，均可在语料内调整。这些数值不修改生产
配置，不作为性能或准确率门槛。首次运行存在解析器冷启动，不宜用耗时比较
算法速度；优先比较证据与实际输出量。

本命令是观察性评测，不挂入常规质量门禁；常规包测试只检查评分公式。
准确率下降、误报或漏报写进报告而不导致测试失败。工具执行错误、无效语料、
证据锚点在源码中消失、文件缺失或输出失败会使命令失败，避免空报告伪装成功。
每次记录语料与每个源码文件的 digest，以区分实现退化和输入变化。源码语义
变化但锚点仍在时，需要人工重新审阅标注，digest 本身不能证明标注仍然正确。

首轮观测中，文本路线出现 3 个必要测试漏项，结构化路线为 0；结构化路线也
产生一个多余文件候选，输出总量更大。完整数字以本机生成报告为准，不能外推
为真实仓库总体准确率。保留这些失败/成本信号，不为获得漂亮分数修改标注。
